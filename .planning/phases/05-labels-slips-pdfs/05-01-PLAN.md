<objective>
Stand up the new service-host client family for the Quiqup-GraphQL-host REST surface (`graph.quiqup.com` prod, `graph.staging.quiqup.com` staging) and ship the FIRST tool against it: `download_pending_labels` (MISS-03 → `GET /pending_orders_labels`).

Rationale: This is a NEW service-host family (per STATE.md decision 2026-05-20 03-04 wording: "New service-host families get their own error class"). Although the upstream is named "Quiqup GraphQL" (per the FE env-var family `VITE_QUIQUP_GRAPHQL_BASE_URL`), the endpoints exposed on it are REST-shaped (`GET /pending_orders_labels`, `GET /return_order_label/{orderId}`, etc.) NOT GraphQL POSTs. This client wraps that REST surface; the file is named `quiqup-graphql-host.ts` to disambiguate from `lib/clients/orders-core-graphql.ts` (which IS a true GraphQL POST client, but for a different host `orders-api.quiqup.com/graph`).

The canonical binary-response envelope `{ contentType, base64, filenameHint }` is REUSED VERBATIM from Phase 3 plan 03-04 — NOT re-derived per-host. The tool returns TWO content blocks (a `resource` block carrying the base64 PDF on `resource.blob`, and a sibling `text` block carrying the JSON metadata envelope) mirroring `lib/tools/download-orders-export.ts`. This is the locked pattern for Phase 5 / Phase 7 CSV / Phase 10 Zoho PDFs.

Purpose: Open Phase 5 with the foundational infrastructure — the new client + its error class + the first tool — so Waves 2 and 3 can reuse the client for the return-label and slip endpoints. Concentrating new-client risk into Wave 1 means Waves 2-3 are pure tool additions against a tested client.

Output: 1 new client module (`lib/clients/quiqup-graphql-host.ts`), 1 new tool spec (`lib/tools/download-pending-labels.ts`), 2 new test files (1 client + 1 tool), `app/[transport]/route.ts` registering the new spec under a Phase-5 Wave-1 comment block, the tool-surface snapshot bump, AND a `CALL-LOG-pending-labels.md` capturing the AGENTS.md-mandatory live-staging call.
</objective>
